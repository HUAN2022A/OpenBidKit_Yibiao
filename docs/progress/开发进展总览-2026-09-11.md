# 易标投标工具箱 · 开发进展总览

> **统计口径**：2026-09-11，`main` 分支
> **项目定位**：开源免费 AI 标书编写桌面工具（AGPL-3.0），Electron + React 19 + TypeScript
> **代码规模**：client 侧约 9.6 万行（TS/TSX/CJS）｜67 个 Main 服务｜23 个 IPC 模块｜30 个页面组件｜14 个功能目录
> **数据库 schema**：v27

---

## 一、一句话结论

**产品主线已经成体系并日常可用**——AI 生成技术方案、已有方案扩写、查重、废标项检查、导出模板四块构成了完整的「导入 → 解析 → 生成 → 检查 → 导出」闭环。

**近两周（9.7–9.10）新增三类能力**：标书质量自评（AI 评标）、资产复用（配图复用 + 图片知识库）、以及投标机会模块（机会发现 / 报价预测 / 企业画像）。

**需要正视的一点**：新增能力中，**投标机会模块是刚落地的半成品**——后端、桥接层、UI 三层代码都已提交，但尚未经过真实数据的端到端验证，也没有配套测试。

## 三、功能全景（按菜单模块）

### 1. 标书生成 —— 核心主流程 ✅ 稳定

| 子能力 | 说明 | 成熟度 |
| --- | --- | --- |
| 生成技术方案 | 招标文件解析（18 个解析项）、多标段、多阶段投标、目录生成、全局事实设定、正文生成（字数无上限）、全文一致性检查、错别字检查、逻辑谬误分析、语义化改写 | ✅ 稳定 |
| 已有方案扩写 | 上传人写的方案 → 优化扩写，与技术方案共用同一套 Store、任务与页面（`workflowKind` 区分） | ✅ 稳定 |
| 配图能力 | AI 生图 / Mermaid 渲染 / HTML 绘图 / **知识库图片复用** | ✅ 稳定（复用为新增） |
| 后台任务模型 | 全部耗时流程在 Main 后台运行，页面卸载不取消，重挂载从快照 + 活动任务回放恢复 | ✅ 稳定 |
| 可行性研究报告 | 独立 7 步流程（来源/素材/分析/参数/目录/正文） | ⚠️ Beta |

### 2. 模版设置 ✅ 稳定

- **我的模板 / 新建模板**：Word 排版与编号格式配置，支持**上传现有模板 Word 自动识别**（规则映射，零模型、离线可用），实测可正确识别中文字体字号、行距、表格边框、页边距。
- **导出格式**：预设模板（含新增「正式投标格式」）、页眉 logo / 右栏 / 下划线、边距行距与页码默认值向真实标书靠拢。

### 3. 知识库 ✅ 稳定

- **文档知识库**：资料 / 案例 / 知识条目、文件夹管理、全局检索（分页 100 条 / 页，越界页码自动回落）。
- **图片知识库**：跨文档聚合所有历史图片，支持缩略图网格、类型筛选、关键词检索、大图预览、溯源跳转。
- **图条目化**：解析文档时保留图片并连同图注、上下文、类型标签入库，是配图复用的数据基础。

### 4. 标书检查 ⚠️ 能力齐但存在断链

| 子能力 | 现状 |
| --- | --- |
| 标书查重 | 多份标书相似度检测 + Excel 导出。**已核实边界**：bid↔bid 正文仍是归一化精确匹配，改写、调序检不出；字符 bigram 相似度仅用于剔除「引用招标原文」的误报 |
| 废标项检查 | 硬性条款与响应完整性检查 + Excel 导出，支持超长标书 |
| AI 评标 | 单评委模拟打分，产出总分、得分率、逐项得分、扣分理由、改进建议与评标报告 |

> 💡 **系统性短板**：四类检查（废标项、查重、AI 评标、一致性审计）**全部「只报告不改写」**——检出结果不定位到目录节点，没有带整改要求的一键重写，用户必须手工回改，检出率无法直接转化为得分。

### 5. 投标机会 —— 最新模块 🟡 半成品

- 拆分为**机会发现 / 报价预测 / 企业画像**三个子页面，含公告解析、评分匹配、线索状态跟踪、URL 导入、后台解析与打分任务。
- 后端（Store 701 行 + 任务 443 行 + SQLite 迁移 v27）、桥接层（IPC/preload/类型）、UI（3 个页面 + 581 行样式）三层均已落地。
- **风险**：无测试覆盖，未经真实招标公告验证，实际召回与打分效果未知。

### 6. 平台与系统能力 ✅ 稳定

- **AI 接入**：统一经 `aiService` 调度，支持所有 OpenAI 兼容接口及 ollama / LM Studio 本地模型，集中处理队列、并发、重试、取消、Token 统计。
- **Pi Agent 运行时**：每任务独立 Runtime / Session，Agent 提问由全局对话框与自动确认服务承接。
- **离线模式**：一键关闭全部运营类出网请求，用户自配的 AI / 解析服务不受影响。
- **插件系统、投标资源下载、在线公告、自动更新、埋点 Analytics**（独立 Cloudflare Worker + Dashboard）。

### 7. 未开发

- **商务标（business-bid）**：仅有硬编码演示占位页面，未接入菜单与路由，属死代码。

## 五、效果评估

### 5.1 成熟度分级

| 级别 | 模块 |
| --- | --- |
| ✅ 稳定可用 | 技术方案生成、已有方案扩写、模版设置与 Word 识别、文档 / 图片知识库、查重、废标检查、导出、离线模式 |
| ⚠️ 可用但待打磨 | 可行性研究报告（Beta）、AI 评标（刚交付）、配图复用（新召回策略） |
| 🟡 半成品 | 投标机会（机会发现 / 报价预测 / 企业画像） |
| ❌ 未开发 | 商务标 |

### 5.2 工程质量

- **架构清晰度**：进程边界（Renderer / preload / Main）职责分明，业务 IPC 保持薄转发、逻辑集中在服务层；Renderer 不直接触达 Node，跨进程契约有单一类型来源。这是这个规模的项目里最扎实的一块。
- **可靠性**：后台任务在 Store 事务中 checkpoint，页面卸载不中断，重启后按任务类型决定恢复策略（正文任务可 paused，目录等待选择仅在 Session 完整时恢复）。产品级可靠性明显优于同类工具。
- **可测性**：**偏弱**——13 个单测面对 9.6 万行代码，且无全量 test / lint 脚本，回归高度依赖手工验证。新模块（投标机会）零测试。
- **安全与合规**：离线模式覆盖面完整；普通埋点不上传 API Key / Prompt / 响应 / 文件内容；密钥不入库。在开源本地客户端场景下尺度合理。

### 5.3 与产品目标的匹配度

当前产品重心是**「标书完成之后如何写得更好」**，而非从零生成。以此为标尺：

- ✅ **已踩在点上**：AI 评标、查重、废标项检查、全文一致性、错别字与逻辑谬误分析，都是完成态标书的诊断手段。
- ❌ **最大价值缺口**：诊断结果**回不到正文**。检查报出的问题没有定位到目录节点，也没有一键整改，检出与修改之间是断的。
- ❌ **规则类检查空白**：报价算术校验、大小写金额互验、工程量清单 diff、限价比对——纯规则、投产比最高的一块完全没有；导出也缺 Word 目录域与页码回溯，做不了「评分点 → 页码」索引表。
- ⚠️ **隐藏约束**：离线模式会门控全部 AI 调用，所有 AI 类检查在离线状态下整体不可用。

### 5.4 主要风险与欠账

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 高 | 投标机会未验证 | 三层代码已落地但零测试、零真实数据验证 |
| 高 | 诊断→修复断链 | 检查能力无法转化为正文修改，价值打折 |
| 中 | 测试覆盖薄 | 13 个单测 / 9.6 万行，且无统一测试脚本 |
| 中 | 规则类检查缺失 | 报价、页码索引、暗标合规零覆盖 |
| 低 | AI 评标单评委 | `judgeCount` 已贯通然而恒为 1，多评委盲评未落地 |
| 低 | 模板识别未接 AI 兜底 | 未知字体字号直接置默认值 |
| 低 | 死代码 | `business-bid` 未接入菜单 |

## 六、下一步建议

1. **先验证再扩展**：给投标机会补真实招标公告的端到端验证，确认召回与打分可用后再考虑加功能。
2. **补齐「诊断 → 改写」闭环**：把检查结果的 finding 定位到 `technical_plan_outline_nodes` 节点，接一键带整改要求重写；同时补 bid 侧从技术方案反读正文的入口（tender 侧已有对应能力，bid 侧缺失）。
3. **优先做规则类检查**：报价算术与大小写互验、限价比对——纯规则、离线可跑、投产比最高。
4. **导出补页码索引**：接入 Word 目录域与页码回溯，支撑「评分点 → 页码」索引表与按页扣分控制。
5. **补测试**：至少给投标机会与新引入的 Store 补齐单测，把回归从手工验证中释放出来。
